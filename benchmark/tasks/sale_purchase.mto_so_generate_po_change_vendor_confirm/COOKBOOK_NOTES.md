- **MTO + Buy seed checklist** (auto-generating a draft RFQ from SO confirmation on a physical product):
  1. `env.ref("stock.route_warehouse0_mto").active = True` — MTO ships inactive in fresh DBs.
  2. `env.ref("purchase_stock.route_warehouse0_buy").product_selectable = True` — Buy ships `product_selectable=False` (warehouse-level only); flip it so the product can carry both MTO and Buy.
  3. `main_wh.buy_to_resupply = True` then `main_wh.write(main_wh._create_or_update_route())` to (re)build the warehouse `mto_pull_id` rule after toggling MTO active.
  4. `mto_route.rule_ids.write({"procure_method": "make_to_order"})` — paranoid; ensures MTO rules actually push procurement upstream instead of falling back to make_to_stock.
  5. Product must be `type='consu'` + `is_storable=True`, with `route_ids = [mto_route, buy_route]` and ≥1 `product.supplierinfo` (first seller by `sequence` is the one selected for the auto-generated RFQ).
- **MTO-generated PO does NOT carry `sale_line_id`** on its `purchase.order.line` — that field is only set for dropship (see `sale_purchase_stock/models/purchase_order.py::_prepare_purchase_order_line_from_procurement` guard `if not values.get('move_dest_ids')`). For MTO the SO<->PO link goes through `stock.reference.purchase_ids` (`sale_purchase_stock.sale_order._get_purchase_orders` override). In check.py, search POs by `origin=SO.name`, NOT by `order_line.sale_line_id.order_id`.
- **`sale.order.purchase_order_count` smart button does cover MTO-generated POs** — the `sale_purchase_stock` bridge makes `stock_reference_ids.purchase_ids` part of the computed count, so the SO form's Purchase button navigates correctly on MTO flows too.
- **Changing `partner_id` on a draft MTO-generated RFQ silently recomputes line `price_unit`** via `purchase.order.line._compute_price_unit_and_date_planned_and_name` (no wizard / no confirmation prompt). Any vendor swap that hits a different `product.supplierinfo` row updates the price; the user just has to save.
- **State-diff with `match_key: [partner_id]` on purchase.order** treats a vendor swap as a delete+create pair of diff rows (old partner key disappears, new partner key appears). `expected_state.json` must include a `delete` op for the old vendor's entity_key plus a `create` op for the new vendor's entity_key — NOT a single `set` on `partner_id`.
